# Per-language pronunciation proposals

Generated by `node scripts/probe-pronunciation-language.js --languages es,fr,de,it,pt,ja,ru --limit 20`,
covering the seven locales the docs ship in. Every entry was synthesised through
MiniMax with that language_boost and transcribed, so `heard` is what the voice
actually produced, not a guess.

**Nothing here is applied.** Each entry needs someone who speaks the language to
confirm the expansion reads naturally and the token is not an ordinary word. See the
hazards section first — a few are unsafe as proposed.

## Hazards found on review — read before applying anything

**Japanese entries now fire — this was fixed, not worked around.** They previously could
not: word boundaries used `\p{L}\p{N}` lookarounds, Kana and Kanji are `\p{L}`, so a Latin
token against Japanese text looked word-internal. Since Japanese has no spaces, that is how
the language is actually written, and these entries would have sat in the dictionary firing
only when a viewer happened to add spaces.

`replaceEngine.js` now treats a **change of script** as a boundary in its own right, so
`それkwskで` expands while `xkwsk` and `kwskx` still do not. English is unaffected.

One consequence to weigh: a digit-only term now matches inside a number written next to
Kanji, so `価格は888円` would fire if `888` were added. See below.

**`888` / `8888` are numbers.** Proposed as applause (`パチパチパチ`). The boundary rule does
protect the common case — `価格は888円` is left alone — but a viewer typing a bare `888`
meaning the number would have it read as applause. The voice already says
「はっぴゃくはちじゅうはち」 correctly, which is the right reading of a number.

**`dnd` → "de nada" (Spanish) is a collision the propose step missed.** Its check is "is this
an ordinary Spanish word", and `dnd` is not — it is an *English* acronym, and Dungeons &
Dragons comes up constantly in stream chat. The voice heard it as "D and D", which is the
correct reading of the thing viewers usually mean.

**Two Spanish proposals leak straight through the profanity filter.** These expand to
profanity that exists only *after* the rewrite, so the filter is the last thing standing —
the same shape as the `wtf` failure in English. Running the real Spanish + English rule set
over each proposed expansion:

| token | expansion | after the filter | |
|---|---|---|---|
| `alv` | a la verga | a la vaya | caught |
| `lpm` | la puta madre | la pilla madre | caught |
| `hdp` | hijo de puta | hijo de pilla | caught |
| `npi` | ni puta idea | ni pilla idea | caught |
| `ctm` | concha tu madre | *unchanged* | **leaks** |
| `csm` | concha su madre | *unchanged* | **leaks** |

`concha` is not in the Spanish list (25 entries). Adding `ctm` or `csm` would put profanity
into the audio of a channel that has filtering switched on. Add `concha` to
`profanityLists.json` first, or leave both out.

**Two-letter tokens** (`tb`, `ns`, `nd`, `nc`, `nf`, `nr`, `nk`, `gj`, `ky`, `ry`) carry the
highest collision risk for the least benefit, and several are also initials or unit
abbreviations. Prefer the three-plus-letter entries.
